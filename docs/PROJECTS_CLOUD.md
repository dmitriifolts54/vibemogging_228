# Проекты, общая папка, обмен V2 и конвертация

Ветка `feature/compact-projects-cloud` поверх компактного хранилища
`feature/compact-media-storage` ([STORAGE_ENGINE.md](STORAGE_ENGINE.md)).
Маршруты API — в [API.md](API.md), раздел «Projects, cloud folder…».

## Запуск

```bash
python3 -m vibemogging                      # список проектов в ~/Vibemogging
python3 -m vibemogging --workspace ~/Видео/Проекты
python3 -m vibemogging --data-dir ~/old-project   # один проект, как в V1
```

`workspace.json` — список папок проектов этого компьютера; он не синхронизируется.
Каждый проект — обычная папка данных со своей блокировкой. Папка V1
`./.vibemogging` попадает в список автоматически. «Убрать из списка» не удаляет файлы.

## Общий проект через облачный клиент

Используется уже установленный Dropbox, Яндекс Диск, iCloud Drive, Google Drive
и т. п.: в его папке создаётся `vibemogging-<id проекта>/`. Сервера, хостинга и
учётных записей нет.

```
vibemogging-<id>/
  project.json                         id и название (пишется один раз)
  objects/<kind>/<id[:2]>/<id>.z       коммиты, манифесты, звук, LUT, отдельные кадры
  assets/<id[:2]>/<id>                 исходные сжатые видео, как импортированы
  recipes/<sha256>.json                пачки рецептов кадров (ссылки на исходники)
  devices/<устройство>/device.json
  devices/<устройство>/snapshot-<время>-<id>.json
```

- Все файлы неизменяемы и адресуются содержимым. Запись — во временный
  скрытый файл, затем атомарное переименование.
- «Опубликовать версии» копирует только отсутствующие файлы и последним пишет
  снимок устройства: ветки, нужные объекты и размер каждого файла.
- Снимки разных компьютеров лежат в разных папках. Общих изменяемых файлов
  (`state.json`, SQLite) в общей папке нет; локальные индекс и состояние остаются
  на каждом компьютере.
- «Получить» принимает только снимок, все файлы которого уже на месте и нужного
  размера. При установке проверяются SHA-256 объектов и исходников, затем
  каждый восстановленный кадр и звуковой блок. Только после этого появляются ветки
  `<устройство>/<ветка>`; при любой ошибке открытый проект не меняется.
- Недосинхронизированный снимок показывается как «облако ещё синхронизирует,
  не хватает N файлов». Повреждённый или обрезанный файл снимка пропускается,
  используется предыдущий полный.
- Публикуются только коммиты локальных веток; черновик остаётся на компьютере.
  Слияние — вручную на вкладке «Слияние». Папка не служит блокировкой: двум
  людям лучше договориться, кто сливает, чтобы не получить два разных merge-коммита.

## `.vmrepo` формат 2

Пакет содержит обычные объекты, рецепты кадров и исходники (`ZIP_STORED`,
потоком). Кадры при экспорте не распаковываются в RGB. Импорт понимает V1 и V2.
Принимающему компьютеру нужна эта версия приложения.

## Конвертация старых проектов

```bash
python3 -m vibemogging.maintenance migrate СТАРАЯ_ПАПКА НОВАЯ_ПАПКА [--source-media исходник.mov]
```

В интерфейсе — кнопка «Компактная копия» в списке проектов.

1. Исходная папка только читается (на время работы она заблокирована от сервера).
   Новая папка собирается под временным именем и переименовывается после проверки;
   при ошибке временная папка удаляется. Существующая папка назначения не трогается.
2. Сохраняются все коммиты, ветки (включая входящие), черновики, незавершённое
   слияние с выбранными вариантами и исходные ID кадров. `state.json` копируется
   без изменений.
3. Если указан исходный видеофайл и он воспроизводит все кадры первой версии
   (проверяются нормализации 1 и 2), кадры ссылаются на него.
4. Кадры V1 «ярче/темнее» распознаются как LUT поверх уже доступного кадра той же
   позиции, только если результат совпадает побайтно.
5. Остальные старые RGB-кадры упаковываются в клипы `libx264rgb -crf 0` по
   240 кадров. Каждый клип декодируется тем же конвейером, что использует Store,
   и сверяется по ID; несовпавшие кадры остаются обычными lossless-объектами.
6. В конце каждый кадр и звуковой блок читается через новый Store с проверкой ID.

## Замеры

25 октября 2026, macOS 27.0.1, FFmpeg 9.0.2, Python 3.14.6. Репозитории V1
созданы кодом `main@56d74eb`: импорт 12 с 1280×720, 25 к/с, звук; ветка с «ярче»
на 00:02–00:04 (50 кадров) и «без звука» на 00:04–00:06. Всего 350 уникальных кадров.

| Материал | V1 | С исходником | Без исходника (lossless-клипы) |
| --- | ---: | ---: | ---: |
| `testsrc2` + шум, исходник 42,3 МБ | 519,1 МБ | **41,9 МБ** (5,5 с) | 475,9 МБ (63 с) |
| `testsrc2` без шума, исходник 4,4 МБ | 66,1 МБ | **5,7 МБ** (2,9 с) | 47,5 МБ (7,2 с) |

Во всех случаях проверено 350 из 350 кадров, ошибок нет. Без исходного файла
выигрыш небольшой: шум и мелкие детали lossless-кодек сжать почти не может.
Конвертация без исходника небыстрая: около 5–6 кадров/с для 1280×720 с шумом на
этом компьютере; для 15 минут это порядка часа. Цифры нельзя переносить на другой
материал без собственного замера.

Прочее на тех же данных:

- `.vmrepo` V2 компактной копии «с шумом» — 43,9 МБ. Пакет V1 того же проекта
  содержал бы все RGB-кадры, порядка размера исходной папки.
- Общая папка, проект 20 с 640×360: первая публикация — 302 файла, 6,1 МБ;
  повторная без изменений — 0 файлов; правка (заливка + «ярче») — 5 файлов,
  44,2 КБ; коммит слияния — 8 файлов, 66,2 КБ.
- Кэш предпросмотров по умолчанию 1 ГиБ на проект. Предпросмотр компактной копии
  «с шумом» — 37,3 МБ; старые MP4 вытесняются по давности использования.

## Проверено

- 61 автоматический тест на ветке после слияния с `1b3cb5e` (`python3 -m unittest
  discover`, все проходят), включая тесты компактного хранилища. Новые тесты этой ветки: обмен V2
  и импорт V1, порча/нехватка объектов и исходников, рецепты источник+LUT после
  обмена, конвертация с историей/черновиком/конфликтом, сохранность исходной папки
  (по SHA-256 всех файлов), откат при ошибке, отказ при существующей папке,
  lossless-запасной путь, исходник+LUT при конвертации, две копии через одну
  общую папку, неполная синхронизация, порченый объект, обрезанный снимок, список
  проектов, HTTP-режимы, ограничение кэша.
- Вручную в Chromium (встроенный браузер) с настоящим backend, два сервера
  на одном компьютере с общей локальной папкой вместо облака: создание проекта,
  импорт, `replace_av` (обе дорожки меняются; слишком короткий источник отклоняется
  без изменений), подключение папки, публикация, получение проекта на втором
  «компьютере», независимые правки, конфликт и его разрешение, совпадение кадров
  с LUT на обеих копиях побайтно, неполная синхронизация (кнопка «Получить»
  отключена, проект не меняется), перемотка после докачки, добавление папки V1,
  компактная копия из интерфейса, открытие копии, экспорт `.vmrepo` V2.

Не проверялось: настоящие облачные клиенты (Dropbox, iCloud и др.) и их поведение
с файлами-заглушками; два физических компьютера; ролики длиннее 20 секунд в
интерфейсе; Firefox и Safari; Windows.

## Ограничения и что согласовать

- Облачная папка не проверяет, что два устройства одновременно сливают одни и те
  же изменения; criss-cross merge по-прежнему не поддерживается (ограничение V1).
- Существующие файлы в общей папке при публикации не перечитываются целиком
  (иначе каждая публикация читала бы весь проект); целостность проверяет получатель.
  Повреждённый в облаке файл нужно удалить вручную, чтобы его опубликовали заново.
- Конвертация без исходника почти не уменьшает материал с шумом и идёт медленно.
- Кадры с заливкой и кадры, не совпавшие при упаковке, хранятся обычными объектами.
- Для контракта: было бы полезно `Store.has_asset(id)` (сейчас проверяется наличие
  файла по `asset_path`) и способ проверить только цепочку зависимостей рецептов без
  полного декодирования — для быстрой проверки длинных снимков.
